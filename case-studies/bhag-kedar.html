Why I built it

My earlier games, such as Tic Tac Toe and Rock Paper Scissors, ran on one screen for one player. I wanted to find out what changes when a game has a real-time loop, several players and a network between them. An endless runner is a good place to start because the rules are simple, but the game has to feel responsive on a phone.

I also wanted it to be a real app that friends could install and play from different countries, not just a page on my laptop. That meant solving hosting, offline support and multiplayer as well as the game itself.

What it does

  • Seven playable runners, with a preview carousel and the option to put your own face on the runner (the photo stays on your device)
  • Six locations, each with its own sky, scenery, road, weather and music scale: Mumbai, Tokyo, Cairo, Rio, London and Himalaya
  • Offline races against one to three computer rivals, with Easy, Normal and Hard difficulty, plus a Practice mode
  • Online races: host a room and share a six-character code, join a friend's room, or tap Quick match to be paired with anyone
  • Samosa boost and power-up buttons, a pause button and sound and music volume settings
  • Touch controls on phones and keyboard controls on desktop (arrows or WASD, Space to jump, Shift to boost, Q or F for power, P to pause)
  • Installable and playable offline for solo races

How it works

Everything is drawn on one canvas. The game screen is a single full-screen canvas. The menus are ordinary HTML laid over it in a panel, which kept the interface easy to style and accessible, while the canvas only has to draw the race. The menu itself is a step flow (name, runner, mode, setup), and each step is a section that is shown or hidden.

Locations are data. Each track is one object in a list: its sky gradient, ground and road colours, weather type, scenery pieces, vehicle plate and a music scale. Adding a seventh location means adding one entry, not writing new drawing code.

{k:"NP", n:"Himalaya", e:"🏔️",
 sky:["#244a92","#86bdee","#f4f9ff"],
 wx:"snow", dc:["pine","pine","bld"],
 mu:{r:247, s:[1,1.125,1.333,1.5,1.778,2]}}

Online play uses a shared database, not a game server. Players connect through Firebase Realtime Database. Each room is a node, and each player writes only their own small record (name and state) under it. Everyone else reads the room and draws the other runners. A separate node holds the Quick match queue and another holds the small player-photo copies.

The database rules do the protecting. Reads and writes are closed by default, and only the room, photo and matchmaking paths are opened. A player record must contain a name and a state, and a photo must be a string under 30,000 characters.

"sprint": {
  "$room": {
    ".read": true,
    "$player": {
      ".write": true,
      ".validate": "newData.hasChildren(['n','st'])"
    }
  }
}

A service worker makes it installable and offline. Game files use a network-first strategy, so an update reaches players right away, with the cache as a fallback when they are offline. Fonts are cached after the first load. Anything that is not on the game's own origin, such as Firebase, goes straight to the network so online play is never served from a stale cache.

e.respondWith(fetch(r).then(n => {
  if (n.ok) { const k = n.clone(); caches.open(V).then(c => c.put(r, k)); }
  return n;
}).catch(() => caches.match(r, { ignoreSearch: true })
  .then(m => m || (r.mode === "navigate" ? caches.match("index.html") : Response.error()))));

Responsive from a phone to a desktop. The panel adapts to portrait and sideways phones, tablets and desktops. A short-height media query shrinks the menu so it still fits when a phone is held sideways, and a reduced-motion query turns off animations for people who prefer that.

Technical lessons

  • Data-driven content scales. Putting each location in a data object made new tracks cheap to add, the same idea I first used for the winning lines in Tic Tac Toe.
  • Multiplayer is mostly about who owns what. Letting each player write only their own record avoids players overwriting each other, and it makes the rules simple to write.
  • Network delay is a design problem. Players on different continents see each other slightly late, so the game smooths other runners' movement instead of showing every update as a jump.
  • Caching needs a strategy per file type. Game files, fonts and database calls each need different rules, and a wrong choice means players run an old version or see stale online data.
  • An installable app is more than a manifest. It also needs https, correctly sized icons including a maskable one, and a clear install path for iPhone, which does not show an install button.
  • Setup guides are part of the product. Most online-play failures come from the database rules not being published, so I wrote a troubleshooting table that maps each error message to its fix.

What I would improve next

  • Add Firebase Authentication so rooms and the Quick match queue are not open to everyone who has the link; today the rules are suited to a friends game, not a public one
  • Add a global leaderboard with server-side score checks
  • Clean up old rooms automatically, so abandoned ones do not stay in the database
  • Add more locations and runners, and let players unlock them
