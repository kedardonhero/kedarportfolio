My Computer Science journey

Kedar Nath Sapkota20266 min read

Studying Computer Science at Louisiana Tech University in Ruston has changed how I think about problems. Before, I looked for the answer. Now I look for the structure of the problem first, and the answer usually follows. This article is about the habits and ideas that made the biggest difference, and how I try to turn classroom concepts into things I can actually run.

Programming is mostly problem solving

When I started, I believed programming was about memorising syntax. It is not. Syntax is the easy part and you can look it up in seconds. The hard part is breaking a vague goal into steps small enough that a computer can follow them.

The routine I now use on almost every problem is:

  1. Write the problem in plain language, including what goes in and what should come out.
  2. Solve a tiny example by hand.
  3. Write the steps as comments or pseudocode.
  4. Turn each step into code and test it before moving on.

Doing the small example by hand is the step I used to skip, and it is the one that catches the most misunderstandings.

Turning concepts into projects

Lectures explain an idea; a project forces me to find out whether I really understood it. Many of the projects on my portfolio began as a way to practise a specific concept:

Habits that made me better

Read the error message first

Early on, I would see a red error and immediately search the internet. Now I read the message slowly. It almost always names the file, the line and the kind of mistake. Reading it fully solves most bugs in under a minute.

Change one thing at a time

If I change five things and the program works, I do not know which change fixed it. If I change five things and it breaks, I do not know which one broke it. Small steps keep the cause visible.

Use version control from the start

Git gives me a safe way to experiment. If an idea fails, I go back to the last working commit. Clear commit messages also leave a record of how a project developed, which I find useful when I return to old code.

Explain it out loud

If I cannot explain a piece of code in simple words, I do not understand it yet. Writing the explanation, as I do in the case studies on this site, exposes the gaps faster than rereading notes.

Choosing several languages on purpose

I work with Python, Java, JavaScript, HTML and CSS, and each one teaches something different. Python lets me test an idea quickly. Java forces me to think about types and structure. JavaScript, HTML and CSS let me put the result in front of someone in a browser. Moving between them separated the concepts that are universal, such as loops, functions and data structures, from the details that belong to one language.

What I found difficult

Progress was not a straight line. Debugging code I did not understand, getting stuck on a project for hours and comparing my progress with other people were all part of it. What helped was treating every bug as information and keeping a list of what I had solved, so that I could see the progress that was easy to forget.

Advice for new Computer Science students

  • Build something small every few weeks, even if it is a game or a calculator. Small finished projects teach more than large unfinished ones.
  • Type code yourself instead of copying it; the typing is part of learning.
  • Ask questions early. Professors and classmates have usually seen your problem before.
  • Keep your projects somewhere public, such as GitHub, so you can see how far you have come.
