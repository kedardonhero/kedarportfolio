From learning to building

Kedar Nath Sapkota20267 min read

Learning a programming language and building something with it are two different skills. Tutorials teach you the first. The second only comes from making projects, and it needs a process. This article describes the process I use to go from "I have an idea" to "it works and anyone can try it", with a worked example from one of my own projects.

Step 1: Shrink the idea

My first ideas are always too big. A "chat app" turns into accounts, rooms, notifications and video calls before I have written a line of code. So I write one sentence describing the smallest version that is still useful.

For my expense tracker, that sentence was: "Let me add an expense and see my total." Charts, categories and saved data came later, one at a time. Having a tiny version that works early keeps motivation high and gives me something to build on.

Step 2: Decide what the data looks like

Before drawing any interface, I decide what information the program has to remember. An expense, for example, needs an amount, a category and a date:

const expense = {
  id: 1,
  amount: 12.5,
  category: "Food",
  date: "2026-10-01"
};

Once I know the shape of the data, most of the program is clear: the screen shows this data, buttons change this data, and saving stores this data.

Step 3: Write the logic before the interface

I build the rules as plain functions that do not touch the page. They are easy to test because they take input and return output. Here is the win check from my Tic Tac Toe game:

const lines = [
  [0, 1, 2], [3, 4, 5], [6, 7, 8],
  [0, 3, 6], [1, 4, 7], [2, 5, 8],
  [0, 4, 8], [2, 4, 6]
];

function checkWinner(board) {
  for (const [a, b, c] of lines) {
    if (board[a] && board[a] === board[b] && board[a] === board[c]) {
      return board[a];
    }
  }
  return null;
}

console.log(checkWinner(["X","X","X","","O","O","","",""])); // "X"

Because the function does not depend on buttons or colours, I can run it in the console with a few boards and know it works before I design anything.

Step 4: Add the interface

With the logic working, the interface becomes a layer that does two things: draw the current data, and call the logic when the user does something. I keep one function that redraws the screen from the data, so the display can never drift out of sync.

Step 5: Break it on purpose

Real users do things I did not plan for. Before calling a project finished I try the awkward cases:

  • Empty input, text in a number box and extremely large values
  • Pressing buttons in an unexpected order or very quickly
  • Refreshing the page in the middle of something
  • A very small phone screen

This step is where bugs like divide-by-zero in a calculator or an off-by-one error in a random range usually show up.

Step 6: Use Git from the first commit

Version control is part of building, not an extra. My usual cycle is small and repeatable:

git init
git add .
git commit -m "Add basic expense form"

# work on the next small feature
git add .
git commit -m "Calculate and display total"
git push origin main

Frequent commits with clear messages mean I can undo a bad idea and see how the project grew. They also give anyone reading my GitHub profile a view of how I work.

Step 7: Publish and write about it

A project that lives only on my laptop teaches me less than one other people can open. Publishing forces me to fix the rough edges, and writing a short explanation of how it works, as I do in my portfolio case studies, shows me what I understand and what I only copied.

The tools I rely on

Java and Python for logic-heavy programs, JavaScript, HTML and CSS for anything that runs in a browser, and Git for history. The tools matter less than the process around them: scope small, model the data, write the logic, add the interface, test the edges, commit often and publish.

What I am working on next

My next goal is to move beyond front-end-only projects: add a backend, a database and user accounts, so that what I build can store data for many people instead of one browser. If you are curious how that goes, see the Expense Tracker case study, where it is first on my list of improvements.
