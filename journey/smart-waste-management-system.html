Building a Smart Waste Management System

Kedar Nath Sapkota20267 min read

Most campus waste collection runs on a fixed schedule. That is simple to manage, but it means trucks stop at bins that are barely used while other bins overflow days before the next visit. For my Computer Science project I wanted to find out what changes when the people responsible for the bins can see their condition live. The result is the Smart Trash Bin system, a complete chain from a sensor on a bin to an alert in a browser.

The problem

An overflowing bin is a cleanliness and health problem. An unnecessary collection stop costs fuel and time. Both come from the same missing piece of information: nobody knows how full a bin is until someone goes to look. I defined four requirements: measure how full each bin is, know where each bin is, show a live status, and alert the user when a bin needs attention.

The architecture: four layers

  1. Sensors (Arduino). An ultrasonic sensor measures the distance to the trash, and a load cell measures weight.
  2. Gateway (Raspberry Pi, Python). Reads the Arduino over serial, calculates a fill level and sends it to the server.
  3. Server (Flask). Stores each bin as JSON and serves it through a small REST API.
  4. Dashboard (HTML, CSS, JavaScript, Leaflet). Shows bins on a campus map, with status, alerts and controls.

Splitting the project this way meant I could test each layer on its own. For example, I could test the dashboard with a script that sends fake readings long before the hardware was wired up.

Layer 1: getting a trustworthy reading

An ultrasonic sensor works by sending a short pulse and timing how long the echo takes to return. The distance is the time multiplied by the speed of sound, divided by two because the sound travels there and back. In practice the readings are noisy. Soft surfaces absorb sound, and sometimes no echo returns at all. To handle this, the Arduino takes three readings, discards invalid ones and keeps the median:

int readDistanceFiltered() {
  int d1 = readDistanceOnce(); delay(10);
  int d2 = readDistanceOnce(); delay(10);
  int d3 = readDistanceOnce();
  if (d1 < 0 && d2 < 0 && d3 < 0) return -1;   // all three failed
  // ... replace invalid values with a valid one, then:
  return median3(d1, d2, d3);
}

The load cell adds a second, independent measurement. An HX711 amplifier converts its tiny electrical signal to a number, and a calibration factor converts that number to kilograms. The Arduino sends both values over serial as one line, such as 23,4.80 (distance in cm, weight in kg).

Layer 2: from two readings to one fill level

The Raspberry Pi converts each sensor to a percentage using calibration points: 55 cm means empty and 8 cm means full for the ultrasonic sensor, and 0 to 10 kg for the load cell. Each percentage is then smoothed with an exponential moving average, which blends every new value with the previous one so a single odd reading cannot make the dashboard jump:

def ema(prev, new, alpha=0.35):
    if prev is None:
        return new
    return alpha * new + (1 - alpha) * prev

Then comes the part I found most interesting: sensor fusion. Each sensor fails in a different way. A bag of light packaging can fill the bin to the top but weigh almost nothing, while a single heavy object can sit at the bottom of a bin that is otherwise empty. If I trusted either sensor alone, I would get false alarms or missed alarms. My rule takes the lower of the two readings by default, which avoids false alarms, but lifts the result when either sensor strongly says the bin is full:

def fuse(height_pct, weight_pct):
    base = min(height_pct, weight_pct)

    if height_pct >= 85 or weight_pct >= 85:
        return max(base, 0.70 * max(height_pct, weight_pct))

    if height_pct <= 10 and weight_pct <= 10:
        return min(height_pct, weight_pct)

    return base

Layer 3: the server decides what silence means

The Pi sends the fill level with an HTTP PUT request every two seconds. The Flask server saves it with a timestamp. The most important design decision here is what to do when data stops arriving. A bin that last reported "40%" three hours ago is not a 40% bin; it is a bin we know nothing about. So the server calculates a status from the time of the last reading and marks the bin offline if nothing has arrived for 10 seconds. The dashboard shows it in grey and leaves it out of alerts.

Layer 4: a dashboard that tells you what to do

The dashboard refreshes every second. Bins are coloured by status: Empty is below 40%, Half is 40% or more, and Full is 80% or more. A map built with Leaflet and OpenStreetMap shows where each bin is, limited to the campus area, and a button opens walking directions in Google Maps.

The alert was the hardest piece to get right. If the dashboard played a sound on every refresh while a bin was full, it would be unbearable within seconds. Instead, the alert plays once every 60 seconds while a bin remains full, and the Acknowledge button silences it for two minutes. Adding and deleting bins asks for a PIN, and every change has an undo option for a few seconds.

Design problems the system had to solve

  • Noisy distance readings. Handled with the three-sample median and an invalid-reading marker.
  • Sensors that disagree. Handled with the fusion rules above.
  • A display that jumps around. Smoothing on the Pi keeps the percentage from swinging with every reading.
  • Silent bins. Offline bins are shown in grey and left out of alerts.

A live demo, and why it is simulated

My portfolio is hosted on GitHub Pages, which only serves static files. It cannot run a Flask server or connect to Arduino hardware. So the live demo runs the same calibration values, smoothing and fusion rule in your browser and generates the sensor readings itself. You can add trash to a bin, empty it or disconnect its sensor and watch the full alert and offline status appear. The case study covers the technical details.

What I would build next

  • A real database with reading history, so the system can show fill-rate trends and predict when each bin will be full.
  • Proper authentication. The PIN in my dashboard is a convenience, not real security, because anything in browser code can be read.
  • Route suggestions that cover only the bins that need emptying.
  • A secure hosted API using HTTPS.

What this project taught me

The biggest lesson was that real data is messy, and most of the engineering is about deciding what to trust: filtering a noisy sensor, combining two imperfect ones, treating silence as information, and warning people without overwhelming them. Writing the code for each layer was the easy part. Choosing the right behaviour was the real work.
